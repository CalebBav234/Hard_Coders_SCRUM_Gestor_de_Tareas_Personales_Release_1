# US-06 y US-07: edición y eliminación de tareas

Implementadas sobre `develop` en la rama `codex/feature/us-06-us-07`. No requieren migraciones nuevas: utilizan `tasks.deleted_at`, `tasks.version` y las vistas existentes.

## Uso desde la página

1. Arranca PostgreSQL, el backend y el frontend como indica el README. Abre `http://localhost:4200`.
2. En una tarjeta, pulsa **Editar**. Modifica título, descripción o prioridad y pulsa **Guardar cambios**. La tarjeta se actualiza con la respuesta del servidor, sin recargar la página.
3. **Cancelar edición** descarta el borrador sin enviar una modificación al backend.
4. **Eliminar** abre una confirmación que identifica la tarea. **Cancelar eliminación** no cambia datos. Solo **Confirmar eliminación** envía la petición y, si el servidor la acepta, retira la tarjeta y actualiza el contador.
5. **Actualizar lista** consulta de nuevo lo persistido. También puedes recargar la página para comprobar que el resultado se conserva.

Durante una edición o confirmación se deshabilitan las otras acciones de las tarjetas; mientras se guarda/elimina, se bloquean envíos duplicados. Si falla la petición, no se muestra un éxito falso ni se oculta la tarea.

## US-06: campos y reglas

- Editables: `title` obligatorio (hasta 160 caracteres y no solo espacios), `description` opcional (hasta 4000), `priority` (`ALTA`, `MEDIA` o `BAJA`).
- Se puede editar una tarea INACTIVA, ACTIVA o TERMINADA.
- No se modifican `status`, `createdAt`, `activatedAt`, `completedAt`, `totalActiveSeconds`, categoría, padre ni relaciones. Los cambios de estado siguen usando sus acciones propias.
- `updatedAt` y `version` sí se actualizan: identifican la modificación. El tiempo efectivo de una tarea ACTIVA sigue avanzando normalmente; la edición no reinicia el segmento activo.
- El frontend conserva el borrador ante errores. Si la versión está desactualizada, informa cómo recuperar la lista actual sin sobrescribir cambios ajenos.

Contrato:

```http
PUT /api/tasks/7
Content-Type: application/json

{"title":"Preparar presentación","description":"Añadir la demo","priority":"ALTA","version":2}
```

Responde `200` con la tarea persistida y su nueva versión. Se envían todos los campos editables; usa `description: null` para quitar la descripción. No es un PATCH parcial.

## US-07: borrado lógico

```http
DELETE /api/tasks/7?version=3
```

Responde `204` sin cuerpo. El identificador y la versión del ejemplo deben sustituirse por los de la tarea actual (`GET /api/tasks`).

- Marca `deleted_at`; no ejecuta `DELETE` físico ni requiere nuevos permisos para `gestor_tareas_app`.
- La tarea desaparece de `v_tasks`, `v_pending_tasks` y de la lista de la aplicación, incluso tras recargar.
- Conserva el registro, su estado y las fechas anteriores, así como el historial de transiciones y relaciones. El historial de auditoría puede consultarse en `v_task_history`; no hay papelera ni restauración desde la interfaz en estas historias.
- Una tarea eliminada no admite edición, activación, completado ni otra eliminación: responde `404`.
- Si tiene subtareas no eliminadas, responde `409` y pide eliminarlas primero. No se borra trabajo adicional en cascada.

## Respuestas controladas

| HTTP | Situación | Qué hacer |
| --- | --- | --- |
| 400 | Título/descripción/prioridad/versión inválidos o versión ausente | Corregir los datos. |
| 404 | Tarea inexistente o ya eliminada | Actualizar la lista. |
| 409 | La tarea conserva subtareas visibles | Resolver primero las subtareas. |
| 412 | Otro cambio incrementó la versión | Conservar el borrador si hace falta, cancelar, actualizar y volver a editar/confirmar. |

La versión es obligatoria en las dos operaciones nuevas. Se comprueba antes de modificar datos y también se aplica el bloqueo optimista de JPA para cambios concurrentes.
