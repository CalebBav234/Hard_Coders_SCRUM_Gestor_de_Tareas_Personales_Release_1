## A. Repository Findings

### Current branch
- The working tree is on a feature short branch per the README flow (feature/US-XX-* off develop). Confirm exact branch name with the user before opening the PR; implementation should land on `feature/US-05-US-08-US-09-US-10-reopen-pause-priority-category` and merge via PR into `develop`.

### Architecture
- Spring Boot 3 / Java 21 / Maven backend (backend/pom.xml), REST JSON on port 8080.
- Angular 22 / TypeScript frontend (frontend/), standalone components, /api proxy configured in angular.json.
- PostgreSQL 18 schema task_manager, Flyway-style versioned migrations in database/migrations/ (V001, V002) applied by database/docker/init-dev-db.sql inside the official postgres:18 container. Roles gestor_tareas_owner (DDL) and gestor_tareas_app (runtime) already exist.
- Backend validates schema at boot with spring.jpa.hibernate.ddl-auto: validate (no DDL from the app).

- frontend/src/app/core/models/task.ts — Task, TaskStatus, TaskPriority, UpdateTaskRequest.
- frontend/src/app/core/services/task.service.ts — listTasks, createTask, updateTask, deleteTask, activate, complete (all funnel through catchError(this.handleError)).

- Client-side status mirror uses Task.status (INACTIVA | ACTIVA | TERMINADA).

### Backend structure (existing)
- controller/TaskController.java — REST endpoints under /api/tasks. Existing actions: POST /, GET /, PUT /{id}, DELETE /{id}?version=, POST /{id}/activate, POST /{id}/complete.
- service/TaskService.java — @Transactional business logic: create, activate, complete, update (title/description/priority only), delete, listTasks. Time accumulation on complete: Instant.now().getEpochSecond() - activatedAt.getEpochSecond() added to totalActiveSeconds, then activatedAt = null, completedAt = now(). Uses verifyVersion for optimistic locking and findVisibleTask for deleted_at IS NULL.
- repository/TaskRepository.java — JpaRepository<Task, Long> plus native queries on task_manager.v_tasks (already returns category_id but not category_name).
- dto/ — TaskResponse (14 fields, includes categoryId, priority, status, activatedAt, completedAt, totalActiveSeconds, effectiveActiveSeconds, version), UpdateTaskRequest (title/description/priority/version), VersionRequest, CreateTaskRequest, ErrorResponse.
- exception/ — GlobalExceptionHandler maps TaskNotFoundException→404 TASK_NOT_FOUND, InvalidTaskStateException→409 INVALID_STATE_TRANSITION, OptimisticLockConflictException→412 VERSION_CONFLICT, validation→400 VALIDATION_ERROR, TaskHasSubtasksException→409 TASK_HAS_SUBTASKS.

### Database (existing)
- task_manager.tasks columns include priority varchar(8) NOT NULL DEFAULT 'MEDIA' with ck_tasks_priority CHECK (priority IN ('ALTA','MEDIA','BAJA')), category_id bigint with fk_tasks_category → categories(id) ON DELETE SET NULL, status varchar(16) constrained to INACTIVA|ACTIVA|TERMINADA, activated_at, completed_at, total_active_seconds, version bigint.
- Constraint ck_tasks_state_timestamps REQUIRES: TERMINADA → activated_at IS NULL AND completed_at IS NOT NULL. Critical insight for US-05: reopening must clear completed_at and set activated_at = now(), which is exactly what the column comment "Última finalización vigente; se limpia al reabrir la tarea" documents.
- task_manager.categories(id, name, created_at, updated_at, deleted_at) already exists with uq_categories_name_active_ci unique while deleted_at IS NULL.
- task_manager.v_tasks exposes category_id but not the category name. We must NOT add a new column; we replace the category_id projection in SUMMARY_COLUMNS with an inline scalar subquery and add a derived category_name column. The entity continues to receive the FK via the existing Task.categoryId.
- No new tables, columns, enums, or migrations are required.

- US-04 complete: taskService.complete(id, version) flips ACTIVA→TERMINADA, accumulates elapsed seconds into totalActiveSeconds, sets completedAt = Instant.now(), clears activatedAt. Returns refreshed summary.
- US-06 update: PUT /api/tasks/{id} body {title, description, priority, version} — already updates priority.
- US-07 delete: DELETE /api/tasks/{id}?version= — logical delete.

### Existing status / priority / category / time handling

- Time: totalActiveSeconds accumulates across completed segments; activated_at is the open segment anchor; effective_active_seconds in the view is computed live.

## C. US-05 Implementation Plan

1. Existing code involved
   - TaskService.activate (template for state transition + timestamp set).
   - TaskService.complete (template for version check — NOT the time-accumulation; reopen must NOT accumulate).
   - Task entity (status, activatedAt, completedAt, totalActiveSeconds, version).
   - TaskRepository.findSummaryById.
   - TaskListComponent action lifecycle (busyTaskId, feedback, loadTasks).
   - task-list.html conditional buttons.

2. Files/classes/components likely affected
   - backend/.../service/TaskService.java — add reopen(Long, Long).
   - backend/.../controller/TaskController.java — add POST /{id}/reopen.
   - frontend/src/app/core/services/task.service.ts — add reopen(task).
   - frontend/src/app/features/tasks/task-list/task-list.ts — add reopen(task) handler.
   - frontend/src/app/features/tasks/task-list/task-list.html — add Reabrir button block.
   - Tests in TaskServiceTest, task.service.spec.ts, task-list.spec.ts.

3. Backend changes
   - Implement reopen:
     - findVisibleTask then verifyVersion.
     - if (!"TERMINADA".equals(task.getStatus())) → throw new InvalidTaskStateException(task.getStatus(), "ACTIVA") → 409.
     - Preserve task.getTotalActiveSeconds() unchanged (US-05 business rule).
     - task.setCompletedAt(null); (clears completed_at).
     - task.setActivatedAt(Instant.now()); (opens new segment).
     - task.setStatus("ACTIVA");.
     - task.setUpdatedAt(Instant.now());.
     - taskRepository.save(task); taskRepository.flush();
     - return toResponse(taskRepository.findSummaryById(taskId));
   - PostgreSQL constraint ck_tasks_state_timestamps is satisfied by clearing completed_at and setting activated_at. Trigger trg_tasks_status_history records TERMINADA → ACTIVA.

4. API contract
   - POST /api/tasks/{id}/reopen with body {"version": <number>}. Response 200 + TaskResponse. Errors: 404 TASK_NOT_FOUND, 409 INVALID_STATE_TRANSITION if state is not TERMINADA, 412 VERSION_CONFLICT.

5. Business-rule changes
   - Previous accumulated active time is preserved (never overwritten).
   - A new active segment begins immediately, accumulating on top of totalActiveSeconds.
   - Only TERMINADA is a legal source state.

6. Persistence behavior
   - UPDATE on task_manager.tasks row; trigger inserts history row TERMINADA → ACTIVA.
   - No new SQL.

7. Frontend changes
   - TaskService.reopen(task): Observable<Task> POSTs /api/tasks/{task.id}/reopen with { version: task.version }.
   - TaskListComponent.reopen(task) mirrors complete(task): set busyTaskId, set feedback on success, call loadTasks(), route errors through handleError.
   - Button rendered when task.status === 'TERMINADA'.

8. State/UI behavior
   - After reopen, list reloads from /api/tasks so the card flips to ACTIVA, activatedAt populates, Pausar/Completar become available, Reabrir disappears.

9. Error handling
   - 409 → "Esta tarea no se puede reabrir porque no está terminada."
   - 412 → handled by existing translation ("La tarea cambió. Actualiza la lista...").
   - 404 → "La tarea ya no está disponible. Actualiza la lista."

10. Integration flow
    - UI click → TaskService.reopen → TaskController.reopen → TaskService.reopen (JPA transaction) → tasks row UPDATE → trigger inserts history → response → loadTasks → UI updates.

11. Potential edge cases
    - Reopen on INACTIVA → 409.
    - Reopen on ACTIVA → 409.
    - Reopen on deleted_at IS NOT NULL → 404.
    - Concurrency: stale version → 412; frontend reload recommended.
    - Total seconds must NOT be reset; the test must verify totalActiveSeconds survives reopen.

12. Why compatible with current architecture
    - Reuses verifyVersion / findVisibleTask / toResponse; matches the activate/complete style; no new dependencies; no schema changes.

   - pause:
     - findVisibleTask; verifyVersion.
     - if (!"ACTIVA".equals(task.getStatus())) → InvalidTaskStateException("ACTIVA", "INACTIVA") → 409.
     - Compute elapsedSeconds = Instant.now().getEpochSecond() - task.getActivatedAt().getEpochSecond(); (same formula as complete).
     - task.setTotalActiveSeconds(task.getTotalActiveSeconds() + elapsedSeconds); — preserves accumulated time.
     - task.setActivatedAt(null);
     - task.setStatus("INACTIVA");
     - task.setUpdatedAt(Instant.now());
     - taskRepository.save(task); taskRepository.flush();

   - POST /api/tasks/{id}/pause body {version} → 200 TaskResponse. Errors 404, 409 INVALID_STATE_TRANSITION (pausing INACTIVA, TERMINADA), 412.

5. Business-rule changes
   - ACTIVA → INACTIVA. Not completion; completed_at stays NULL.
   - totalActiveSeconds accumulates the just-finished segment; not reset.
   - Reactivation uses the existing POST /activate (US-03), which starts a new segment on top.

6. Persistence behavior
   - UPDATE on tasks row. Trigger inserts ACTIVA → INACTIVA. No schema change.

7. Frontend changes
   - TaskService.pause(task) mirrors complete(task) HTTP call.
   - TaskListComponent.pause(task) mirrors complete(task) UI lifecycle: busyTaskId, feedback, loadTasks(), error handling.
   - Button rendered when task.status === 'ACTIVA', placed next to Completar.

8. State/UI behavior
   - After pause, card flips to INACTIVA, Activar appears, Pausar/Completar disappear, time freezes (open segment gone, accumulated total persists in DB).

9. Error handling
   - 409 → "Solo se pueden pausar las tareas activas." (extend handleError mapping or rely on err.error?.message).
   - 412 / 404 reuse existing translations.

10. Integration flow
    - UI click → TaskService.pause → POST /api/tasks/{id}/pause → TaskService.pause (transaction) → tasks UPDATE + history INSERT → loadTasks → UI updated.

11. Potential edge cases
    - Pause on INACTIVA → 409.
    - Pause on TERMINADA → 409.
    - Pause on a deleted task → 404.
    - Concurrency → 412.
    - Re-activate after pause must keep the historical totalActiveSeconds; verified because only pause/activate write that field.

12. Why compatible
    - Reuses the time formula already in complete; mirrors the existing pattern; no schema change; status names already exist; trigger supports the transition.

## G. Cross-Story Integration

### Flow 1 — Create → Activate → Pause → Reactivate
1. POST /api/tasks → INACTIVA, priority=MEDIA, categoryId=null, totalActiveSeconds=0.
2. POST /api/tasks/{id}/activate (US-03) → ACTIVA, activatedAt=now(), version=1. UI shows Pausar / Completar.
3. POST /api/tasks/{id}/pause (US-08) → INACTIVA, activatedAt=null, totalActiveSeconds += elapsed. UI shows Activar. Constraint ck_tasks_state_timestamps is satisfied.
4. POST /api/tasks/{id}/activate (US-03) → ACTIVA, new activatedAt, accumulated time preserved. Constraint satisfied.

### Flow 2 — Create → Activate → Complete → Reopen → Continue
1. Create → activate → 60 s elapse → POST /api/tasks/{id}/complete (US-04) → TERMINADA, totalActiveSeconds=60, completedAt=now(), activatedAt=null.
2. POST /api/tasks/{id}/reopen (US-05) → ACTIVA, activatedAt=now(), completedAt=null, totalActiveSeconds=60 (preserved).
3. 30 s elapse → POST /api/tasks/{id}/complete (US-04) → TERMINADA, totalActiveSeconds=90, completedAt=now(). History rows written by the trigger: null→INACTIVA, INACTIVA→ACTIVA, ACTIVA→TERMINADA, TERMINADA→ACTIVA, ACTIVA→TERMINADA.

### Flow 3 — Create → Assign priority → Persist → Refresh → Display priority
1. Create returns priority=MEDIA; card shows "■ Media".
2. Open editor (US-06), change priority to ALTA, save → PUT /api/tasks/{id} returns priority=ALTA. Card merges, shows "▲ Alta" with red hierarchy.
3. Page reload → GET /api/tasks returns ALTA; UI renders consistent label + color.

### Flow 4 — Create → Assign category → Persist → Refresh → Display category
1. GET /api/categories returns existing categories; the inline select is populated.
2. Select a category → PUT /api/tasks/{id}/category returns updated categoryId + categoryName. Card chip displays the name.
3. Page reload → GET /api/tasks returns the same FK; the view joins and surfaces categoryName.

### Coexistence checks
- Priority and category changes do NOT touch status, activated_at, completed_at, total_active_seconds, version audit row (priority already verified by editingOnlyChangesAllowedFields; we add an analogous test for category).
- Reopen / pause / complete are the only writers of status, activated_at, completed_at, total_active_seconds. They share findVisibleTask + verifyVersion; no race with the priority/category PUT.
- The single TaskRepository.SUMMARY_COLUMNS projection is the single point we extend; all endpoints return the same columns consistently.

## K. Risk Analysis

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Reopening a TERMINADA task could violate ck_tasks_state_timestamps | US-05 fails to persist | Reopen must null completed_at and set activated_at = now(); verified by the constraint (test via TaskServiceTest + DB round-trip). |
| Pause could overwrite or reset accumulated time | US-08 fails business rule | Use the same += elapsed formula as complete; test asserts totalActiveSeconds increases by the elapsed amount. |
| Stale frontend version on action → silent success | Misleading UX | Reuse verifyVersion → 412 → existing handleError translation; UI does NOT mutate local state on error. |
| API contract mismatch between summary columns and toResponse | Backend crash on list/activate/complete/etc. after the new category_name column | Update SUMMARY_COLUMNS and toResponse together; update all test row() helpers atomically; run mvn test. |
| Assigning a soft-deleted category id | FK violation surfaces as raw DB error | Pre-check existence with deleted_at IS NULL in changeCategory; return friendly 404. |
| Priority persisted but invisible in list | AC7/US-09 missed | Update task-list.html markup and CSS in the same PR as backend. |
| Reactivation after pause losing accumulated time | Data loss | Only pause/activate write totalActiveSeconds; activate does NOT touch it. Verify with a service-level test that covers activate→pause→activate→complete and asserts the cumulative seconds. |
| Backward compatibility | Existing US-01..US-07 tests break | Keep UpdateTaskRequest and PUT /api/tasks/{id} contract identical; only ADD new endpoints and a single derived column. Extend TaskEditingTest rather than rewrite. |
| Race between category change and pause | Stale version 412 | Both endpoints funnel through verifyVersion; UI actionsDisabled already blocks concurrent submissions on the same task card. |
| Frontend reuses local optimistic state on error | Misleading UX | New handlers only commit to tasks[] after the server response; on error, state stays as the previous persisted value and the UI shows the error via feedback. |
