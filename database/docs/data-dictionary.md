# Diccionario de datos (V004 - Gestor de Proyectos)

Implementado por `database/migrations/V004__project_management_model.sql`. Diagrama: [../diagram/erd.mmd](../diagram/erd.mmd).

## Criterios transversales

- Claves primarias `integer GENERATED BY DEFAULT AS IDENTITY` (JPA `GenerationType.IDENTITY`), excepto las claves compuestas de `task_assignment`, `project_plan_history` y `task_plan_history`.
- Cadenas `varchar(n)`; textos obligatorios no pueden ser solo espacios.
- Fechas con `timestamptz`; la base trabaja en UTC y la interfaz convierte a la zona del usuario.
- Moneda fija **BOB**: `numeric(15,2)`, `>= 0` y finito (se rechaza `NaN`). Tipo de cambio `numeric(18,6)`, `> 0`.
- Tiempos en **minutos** (`integer >= 0`).
- `updated_at` se actualiza por trigger (`task_manager.set_updated_at()`).
- No hay borrado lógico: proyecto → etapa → actividad → tarea → subtarea se eliminan en cascada. Los usuarios no se borran: se desactivan con `is_active = false`.

## Catálogos (solo lectura para la aplicación)

| Tabla | Valores iniciales |
|---|---|
| `project_status` | `PLANIFICADO`, `EN_EJECUCION`, `EN_PAUSA`, `FINALIZADO`*, `CANCELADO`* (*`is_closed = true`) |
| `work_status` | `PENDIENTE`, `EN_PROGRESO`, `COMPLETADA`* , `CANCELADA` (*`is_completed = true`) |
| `task_priority` | `ALTA` (1), `MEDIA` (2), `BAJA` (3); `name` y `sort_order` únicos, `sort_order > 0` |
| `exchange_rate_source` | `Banco Central de Bolivia` (`https://www.bcb.gob.bo`) |

`is_enabled` permite retirar un valor sin borrarlo. Se recomienda que el backend busque los valores por `name`, no por id.

## `app_user`

| Columna | Tipo | Nulo | Regla |
|---|---|---:|---|
| `user_id` | `integer` | No | Identidad. |
| `email` | `varchar(254)` | No | Único; se guarda en minúsculas y sin espacios. |
| `password_hash` | `varchar(255)` | No | Hash (BCrypt u otro); nunca texto plano. |
| `given_names` / `family_names` | `varchar(100)` | No | No vacíos. |
| `is_chief` | `boolean` | No | Jefe de proyecto; `false` por defecto. |
| `is_active` | `boolean` | No | `true` por defecto. |
| `created_at` / `updated_at` | `timestamptz` | No | Auditoría. |

## Jerarquía de trabajo

| Tabla | Padre (`ON DELETE CASCADE`) | Columnas propias |
|---|---|---|
| `project` | — | `name`, `description`, `manager_user_id`, `project_status_id`, `budget_bob`, `estimated_duration_minutes`, `created_by_user_id` |
| `stage` | `project_id` | `name`, `description`, `work_status_id` |
| `activity` | `stage_id` | `name`, `description`, `work_status_id` |
| `task` | `activity_id` | `title`, `description`, `work_status_id`, `task_priority_id`, `allocated_budget_bob`, `estimated_duration_minutes`, `actual_duration_minutes`, `completed_at`, `completed_by_user_id` |
| `subtask` | `task_id` | `title`, `description`, `work_status_id`, `completed_at`, `completed_by_user_id` |

- `name`/`title`: `varchar(160)`; `description`: `varchar(2000)`.
- En `task` y `subtask`, `completed_at` y `completed_by_user_id` van juntos (ambos nulos o ambos definidos) y `completed_at >= created_at`.
- Todas tienen `created_at` y `updated_at`.

## `task_assignment`

Clave `(task_id, worker_user_id)`: un trabajador se asigna una sola vez por tarea. `assigned_by_user_id` registra quién delegó y `assigned_at` cuándo.

## Historiales (solo `SELECT` e `INSERT` para la aplicación)

| Tabla | Clave | Contenido |
|---|---|---|
| `project_plan_history` | `(project_id, revision_number >= 1)` | `budget_bob`, `estimated_duration_minutes`, `exchange_rate_quote_id` opcional, `changed_at`, `changed_by_user_id`, `reason` |
| `task_plan_history` | `(task_id, revision_number >= 1)` | `allocated_budget_bob`, `estimated_duration_minutes`, `exchange_rate_quote_id` opcional, `changed_at`, `changed_by_user_id`, `reason` |
| `task_status_history` | `task_status_history_id` | `previous_status_id` (nulo en el primer registro), `new_status_id` distinto del anterior, `changed_at`, `changed_by_user_id`, `reason` |

**Cardinalidad 1..\*:** triggers de restricción diferidos (`DEFERRABLE INITIALLY DEFERRED`) exigen, al hacer `COMMIT`, que:

- todo `project` tenga al menos una fila en `project_plan_history`;
- toda `task` tenga al menos una fila en `task_plan_history` y otra en `task_status_history`.

Por eso el backend debe crear el proyecto/tarea y su revisión 1 (y el estado inicial) **en la misma transacción** (`@Transactional`).

## Tipo de cambio

- `exchange_rate_quote.rate_kind`: `COMPRA`, `VENTA` o `REFERENCIA`.
- `bob_per_usd`: bolivianos por dólar, `numeric(18,6) > 0`.
- `quoted_at`: fecha de la cotización en la fuente; `recorded_at`: fecha de registro.

## Datos del modelo anterior

V004 archiva las tablas de V001-V003 sin cambios en el esquema `task_manager_legacy` (la aplicación no tiene permisos sobre él) y traslada las tareas existentes a un **Proyecto legado**:

| Anterior | Nuevo |
|---|---|
| categoría | actividad de la "Etapa legado" (más "Sin categoría") |
| tarea raíz | `task` (mismo id) |
| tarea hija o nieta | `subtask` de su tarea raíz (mismo id) |
| `INACTIVA` / `ACTIVA` / `TERMINADA` | `PENDIENTE` / `EN_PROGRESO` / `COMPLETADA` |
| `deleted_at` no nulo | `CANCELADA` + transición en el historial |
| `total_active_seconds` | `actual_duration_minutes` (redondeo hacia arriba) |
| `task_status_history` | `task_status_history` |

Las operaciones quedan a nombre del usuario técnico inactivo `migracion.v004@gestor-tareas.local`. Etiquetas, relaciones y segmentos de tiempo solo quedan en el archivo. Cuando el equipo ya no lo necesite: `DROP SCHEMA task_manager_legacy CASCADE;`.
